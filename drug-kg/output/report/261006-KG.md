## 1. 웹 페이지 내용 수집 방법

### 1.1 대상 선정과 URL 결정
- Drugs.com에는 순위 페이지가 없어(홈페이지의 알파벳순 "인기 약 100개" 목록만 존재) **ClinCalc DrugStats 처방량 순위 상위 50개 중 Drugs.com 페이지가 있는 약**을 사용했습니다 (`drugs/top50.yaml`).
- URL은 generic 이름을 slug로 바꿔 `https://www.drugs.com/<slug>.html`을 시도하고, 실패하면 후보 slug를 순서대로 시도합니다. 결과는 `data/drug_urls.json`에 저장되어 재사용됩니다.
- 기본 slug가 아닌 경우 4건: Dextroamphetamine+Amphetamine → `adderall`, Fluticasone → `flonase`, Acetaminophen+Hydrocodone → `hydrocodone-acetaminophen`, Ergocalciferol → `mtm/ergocalciferol` (404 4회 후 대체 slug로 해결).

### 1.2 접근 차단과 대응 (Akamai Bot Manager)
- `robots.txt`는 AI 크롤러(ClaudeBot, GPTBot 계열 등)를 전면 차단하고, 일반 UA에는 `/api/`, `/search.php`, `/drug-interactions-all/` 등 일부 경로만 금지합니다. 약 상세 페이지는 허용 경로입니다.
- 단순 `curl`은 403(Access Denied)이었고, 아래 조합으로 200을 얻었습니다.
  1. Chrome과 동일한 헤더 세트(User-Agent, Accept, Accept-Language, Sec-Fetch-*, sec-ch-ua 등)
  2. `requests.Session`으로 홈페이지를 먼저 열어 쿠키(`bm_s`, `bm_so`, `ddc-detect-cookie`)를 받은 뒤 요청
  3. 요청 간 6~10초 랜덤 지연
- 그래도 간헐적으로 403이 발생해(총 **33회**) 다음 복구 로직을 넣었습니다: 403/429 시 45초 × 시도횟수 대기 → 세션(쿠키) 폐기 후 새 세션으로 재워밍업 → 최대 4회 재시도 → 그래도 실패하면 Internet Archive(Wayback) 스냅샷 폴백(이번 실행에서는 0회 사용).
- 받은 HTML은 `data/raw_html/`에 캐시되어 재실행 시 네트워크를 쓰지 않습니다. 수집에는 403 대기를 포함해 약 39분이 걸렸습니다(50페이지, 실측 로그 기준).

### 1.3 페이지 파싱 (`drugkg/parse.py`)
한 페이지에서 두 종류의 정보를 뽑습니다.

**(a) 구조화 메타데이터** (LLM 없이 규칙 기반, 고정밀)
- `h1` 제목, `p.drug-subtitle`: generic name과 발음, brand names(단종 여부), dosage forms와 strengths, drug class(링크)
- JSON-LD(`MedicalWebPage`): 설명, 최종 수정일, 검수자. `FAQPage`: Q&A 목록
- 정보 박스: 처방 구분(Rx/OTC), CSA 통제약물 등급, FDA 승인 연도
- "Related/similar drugs" 캐러셀: 관련 약 10개

**(b) 섹션 텍스트**: `<main>` 안의 `h2`마다 다음 `h2` 전까지의 형제 요소를 평탄화합니다. `p`는 문단, `ul/ol`은 "- 항목", `h3`는 "소제목:" 줄, `dl`은 "용어: 정의", 표는 "셀 | 셀", `details`는 summary+본문으로 바꾸고, 광고/상호작용 검색 박스/캐러셀(`ddc-box`, `ddc-mgb`, `ddc-carousel`, `noprint` 등)은 건너뜁니다. "More about", "References", "Related drugs", "Popular FAQ" 같은 비본문 섹션은 제외합니다.

### 1.4 청킹 (`drugkg/chunk.py`)
- 섹션 단위로 문단을 모아 **최대 1,100자** 청크를 만들고, 150자 미만의 꼬리 청크는 앞 청크에 합칩니다. 긴 문단은 문장 단위로 나눕니다.
- 각 청크에는 `chunk_id`(slug#section#번호), 약 이름, 섹션 제목, 원문 URL이 붙어 최종 트리플까지 provenance로 전달됩니다.
- 결과: 834 청크, 총 570,620자. 섹션별 청크 수: dosage 132, side-effects 112, before-taking 85, warnings 77, interactions 72, uses 59, directions 52, overdose 48, missed-dose 46, what-to-avoid 46, 기타 105.

### 1.5 데이터 이용 주의
Drugs.com 콘텐츠는 저작권이 있으므로 수업 과제용 비상업적 사용에 한정하고, 모든 트리플에 원문 URL과 섹션/청크 id를 남겨 출처를 추적할 수 있게 했습니다.

## 2. 현재 KG 생성 절차

```
raw HTML ─parse─▶ 메타데이터 + 섹션 텍스트 ─chunk─▶ 834 청크
                        │                              │
                        │                     ① Extract (OIE, few-shot)  → 11,140 open triplets
                        │                     ② Define (관계 정의 생성)
                        │                     ③ Canonicalize (정의 임베딩 top-5 검색 + LLM 다지선다, 실패 시 스키마 확장)
                        ▼                              ▼
              구조화 트리플 969개            정규화 트리플 10,411개 (스키마 40 → 193)
                        └──────────────┬───────────────┘
                     ④ Consolidate (확장 관계 병합) ⑤ 후처리(별칭·타입·중복) ⑥ Export
```

### 2.1 실행 환경
- vLLM 0.31로 Qwen3-4B-Instruct-2507을 OpenAI 호환 API(`localhost:8000/v1`)로 서비스. GPU(RTX 3090 Ti 24GB)를 다른 작업과 공유해야 해서 7B 대신 4B를 썼습니다(메모리 50%).
- 관계 정의 임베딩은 bge-base-en-v1.5(CPU). 모든 LLM 호출은 `output/cache/llm/`에 캐시되어 재실행과 재개가 무료입니다. 동시 요청 16개로 vLLM이 배치 처리합니다.

### 2.2 ① Extract: Open Information Extraction
- 논문의 OIE 템플릿을 사용하되, 청크마다 "이 텍스트는 Drugs.com의 **{약 이름}** 페이지 {섹션}에서 왔고 this medicine/it은 {약 이름}을 가리킨다"는 컨텍스트를 넣어 대명사를 약 엔티티로 해소했습니다.
- 약 도메인 few-shot 5개(uses/warnings/side effects/interactions/dosage 예시)를 제공하고, 소형 모델의 스키마 폭발을 막기 위해 "관계명은 재사용 가능한 2~4단어의 일반적 표현, 구체 내용(용량·대상·조건)은 object에"라는 지침을 추가했습니다. 지침 추가 전 첫 약에서 확장 관계 12개가 생기던 것이 5개로 줄었습니다.
- 출력은 JSON 리스트이며, 파싱 실패 시 논문 코드와 같은 괄호 매칭 폴백으로 복구합니다. 결과: 834 청크 모두에서 추출 성공, 11,140 open triplets, raw 관계 1,409종(상위: has side effect 1,788, interacts with 756, has administration instruction 716, has warning 664, treats 373).

### 2.3 ② Define: Schema Definition
- 청크와 그 청크의 트리플, 관계 목록을 주고 관계마다 "subject/object 방향이 드러나는 일반적 정의" 한 줄을 생성합니다(논문 템플릿 + 도메인 few-shot 3개).
- 예: `has withdrawal symptom: When the subject drug is stopped abruptly, the patient may experience the symptom specified by the object entity.`
- 이 정의가 다음 단계의 검색 키가 되므로, 관계 **이름**이 아니라 **의미**로 정규화가 이뤄집니다.

### 2.4 ③ Canonicalize: 시드 스키마 정렬 + 자기 정규화(하이브리드)
- 시드 스키마 40개 관계(`schemas/drug_seed_schema.csv`): treats, has side effect, has serious side effect, interacts with, contraindicated in, use with caution in, has recommended dose, has dosage form, belongs to drug class, has mechanism of action, has boxed warning, has administration/missed dose/overdose/storage instruction 등. 각 관계에 subject/object 타입(Drug→Condition 등)을 함께 정의했습니다.
- 절차: (1) 관계명이 이미 스키마에 있으면 그대로(direct). (2) 아니면 정의 임베딩으로 스키마에서 top-5 후보를 찾고, 논문의 검증 프롬프트로 "A~E 중 대체 가능한 관계 / F. None of the above"를 LLM에 묻습니다(mapped). (3) None이면 같은 배치에서 새로 추가된 관계와 먼저 비교(mapped_new)한 뒤, 정의와 LLM이 부여한 타입을 붙여 스키마에 추가합니다(enriched).
- 결과(11,140건): direct 6,928 (62.2%), mapped 4,022 (36.1%), mapped_new 35, auto 2, **enriched 153 (1.4%)**. 하이브리드 모드라 버려진 트리플은 없습니다.
- 스키마 크기 추이: 40 → 45(1개 약) → 135(26개) → 193(50개). 뒤로 갈수록 증가가 완만해졌고, 확장 관계 153개 중 5회 이상 쓰인 것은 61개입니다.

### 2.5 ④ Consolidate와 필터
- 추출 종료 후 확장 관계끼리(또는 시드와) 정의 유사도 0.80 이상인 후보에 대해 "두 관계가 같은 의미인가?"를 LLM에 yes/no로 묻고 병합합니다. 4B 모델은 명백한 동의어(`is used to treat`→`treats`)에만 yes를 내서 자동 병합은 0건이었고, `has instruction` → `has administration instruction` 1건을 수동 병합(`config.yaml`)했습니다.
- 1회만 쓰인 확장 관계는 최종 KG에서 제외(193 → 147 관계).

### 2.6 구조화 트리플 (969개)
파싱한 메타데이터를 고정밀 트리플로 추가합니다: has generic name, has brand name(204), belongs to drug class(110), has dosage form(224), has strength(234), similar to(496, 관련 약 캐러셀), has availability, fda approval year, has controlled substance schedule.

### 2.7 ⑤ 후처리와 ⑥ 내보내기
- 약 별칭(제목, "this medicine", slug, 괄호 약어 HCTZ 등)을 약 노드로 통합, 엔티티 문자열 정규화(관사·따옴표·구두점 제거, 소문자 키), 관계의 도메인/레인지 타입으로 엔티티 타입을 투표 결정(Drug 우선), (subject, relation, object) 중복 제거 후 등장 횟수·출처 약·청크 provenance를 보존.
- 출력: `triples.jsonl/csv`, `entities.csv`, `schema.csv`, `neo4j/`(nodes/relationships CSV + Cypher), `kg.ttl`(RDF), `kg.graphml`, `stats.json`.

### 2.8 논문(EDC) 대비 구현 차이
| 항목 | 논문 | 본 구현 |
|---|---|---|
| 입력 단위 | 문장 1개 | 섹션 기반 청크(~1,100자) + 약 이름/섹션 컨텍스트 |
| LLM | GPT-3.5/4, Mistral-7B | Qwen3-4B-Instruct (로컬) |
| 임베더 | e5-mistral-7b-instruct | bge-base-en-v1.5 |
| 스키마 | Target alignment 또는 Self-canonicalization | 하이브리드: 도메인 시드 40개 + 확장, 관계 타입(도메인/레인지) 부여 |
| 정규화 병렬화 | 순차 | 배치 검증 후 신규 관계만 순차 중복검사 |
| 추가 단계 | - | Consolidate(확장 관계 병합), 구조화 메타데이터 트리플, provenance, 다중 포맷 내보내기 |
| Refinement (EDC+R) | 스키마 리트리버 + 엔티티 힌트 | 구현됨(`--iterations 1`), 비용 때문에 기본 실행에서는 미사용 |

### 3.2 연결성 (KG로서의 유용성)
- 2개 이상의 약이 공유하는 object 엔티티 1,074개, 10개 이상이 공유하는 엔티티 103개. 가장 많이 공유: allergic reaction(47개 약), nausea(43), headache(39), vomiting(36), dizziness(36), diarrhea(32). 따라서 "같은 부작용을 가진 약", "특정 조건에 금기인 약" 같은 교차 질의가 가능합니다.
- 50개 약 사이의 직접 엣지 100개: similar to 50, interacts with 34(예: Adderall→Tramadol, Apixaban→Clopidogrel/Ibuprofen/Warfarin), increases level of 6, used in combination with 4, should be avoided with 3.
- 같은 drug class로 묶이는 그룹: SSRI(Escitalopram, Fluoxetine, Sertraline), Statins(Atorvastatin, Rosuvastatin, Simvastatin), PPI(Omeprazole, Pantoprazole) 등 2-hop 질의 가능.
- 같은 트리플이 서로 다른 청크에서 2회 이상 추출된 경우 661건으로, 반복 추출이 신뢰도 신호로 쓰일 수 있습니다(`count` 필드).

### 3.3 품질 관찰 (샘플 검토)
좋은 예:
- `Bupropion — has maximum dose → 450 mg/day in up to 4 divided doses`
- `Metformin — contraindicated in → severe kidney disease`, `Metformin — requires monitoring of → estimated glomerular filtration rate`
- `Simvastatin — increases level of → HDL cholesterol`, `Apixaban — interacts with → Warfarin`
- `Sertraline — has onset of effect → up to 12 weeks`

문제 유형과 비율(추정):
1. **관계 오선택**: `Pantoprazole — has warning → blood in urine`(serious side effect가 맞음), `Metformin — lowers level of → acne`, `Bupropion — treats → weight gain`. 4B 검증기가 후보 중 가장 비슷한 것을 고르면서 생기는 오류로, 가장 흔한 품질 문제입니다.
2. **주어 오류**: 주어가 약이 아닌 트리플 13건(0.1%). 예: `regular ovulation — has mechanism of action → reduced androgen levels`.
3. **문장형 object**: Instruction/Warning 타입 1,600여 개는 "take only once daily with evening meal"처럼 문장에 가까워 노드로서 재사용성이 낮습니다. 정보는 보존되지만 그래프 질의에는 덜 유용합니다.
4. **비정보성 공유 노드**: `report side effects to FDA at 1-800-FDA-1088`(47개 약), `call Poison Help line`(39), `seek emergency medical attention`(39) 같은 상용구가 허브 노드가 됩니다. 제거 목록(`postprocess.drop_relations` 또는 엔티티 필터)으로 정리 가능.
5. **엔티티 변형**: `Adderall`/`Adderall XR`, `Albuterol Inhalation`/`albuterol`, `Furoscix ReadyFlow`처럼 제형·브랜드 변형이 별도 노드로 남습니다. object 쪽에 관계어가 섞인 경우도 있습니다(`treats ADHD`).
6. **확장 관계의 질**: 상위 확장 관계 `has maximum dose`(72), `has inactive ingredient`(61), `has withdrawal symptom`(47), `has disposal instruction`(21), `not used to treat`(29)는 시드에 없던 유용한 관계인 반면, `has product variation`, `has side effect variation`, `should not be taken`처럼 모호한 것도 있습니다. 시드 보강 후보로 상위 확장 관계를 검토하는 것이 다음 반복에서 효과적입니다.

### 3.4 한계와 개선 계획
- **모델 크기**: 정규화 검증과 OIE 품질은 모델에 크게 좌우됩니다. GPU가 비면 Qwen2.5-7B-Instruct 이상으로 `--stage extract --force` 재실행(프롬프트 캐시는 모델별로 분리)을 권장합니다.
- **정량 평가 부재**: 현재는 샘플 검토만 수행했습니다. 발표 전 관계별 층화 샘플 100~200개를 수동 채점해 정밀도를 보고하는 것을 제안합니다(`triples.jsonl`의 provenance로 원문 대조 가능).
- **엔티티 정규화**: 브랜드/제형 변형 병합, 상용구 노드 제거, Instruction 타입의 object 요약(짧은 정규형)이 필요합니다.
- **타입 제약 검증**: 관계의 도메인/레인지 타입과 엔티티 타입이 어긋나는 트리플(예: treats → SideEffect)을 자동으로 표시하면 오선택 관계를 걸러낼 수 있습니다.
- **커버리지 확대**: `config.yaml`의 `scrape.pages`에 `sfx`(부작용 상세), `dosage`(용량 가이드)를 추가하면 부작용/용량 정보가 크게 늘어납니다. EDC+R(`--iterations 1`)도 재현율 향상에 도움이 됩니다.
