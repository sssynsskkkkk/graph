# Report: Rebuilding the KG with a 14B Model (2026-10-08)

- Scope: top 50 drugs on Drugs.com (ClinCalc top prescriptions ∩ Drugs.com); follow-up to the KG built with a 4B model on 10-06
- Model: Qwen3-14B-AWQ (4-bit AWQ, vLLM 0.31, thinking disabled); embedder BAAI/bge-base-en-v1.5
- Code: `run_experiment.py`, `drugkg/inputs.py`, `drugkg/entity_canon.py`, `scripts/run_experiments.sh`, `scripts/compare_experiments.py`, `scripts/visualize_kg.py`
- Outputs: `output/experiments/<experiment>/`, `output/report/experiments_comparison.md`, `output/viz/`
- Related reports: `261006-KG_en.md` (construction report, 4B), `261007-experiments.md` (experiment details, Korean)

---

## 1. Why this was done

1. **Model quality.** The 10-06 run used a 4B model because the GPU was shared with other jobs. Its verifier often answered "None of the above" during relation canonicalization, so the schema grew to 107 enriched relations and some relation choices were odd. With the full 24 GB GPU available, the same pipeline had to be re-run with a larger model to measure the difference.
2. **Effect of preprocessing.** A teammate produced a Code-KG style decomposition of complex sentences into simple ones (`data/final_sentences_keep_incomplete.jsonl`, 12,298 sentences). Whether decomposed sentences actually help EDC extraction had to be tested against the raw text under identical conditions.
3. **Need for entity canonicalization.** EDC canonicalizes relations only. The 10-07 audit found that about 48% of the 6,544 entities had surface-form duplicates, sentence-like labels, or split aliases. We wanted to see how much an existing published method, applied as-is, would fix.

## 2. What was done

### 2.1 Model swap
- Downloaded Qwen3-14B-AWQ (9.4 GB of weights) and served it with vLLM (90% GPU memory, 8K context, up to 48 concurrent requests). Qwen3's thinking mode is disabled through a request option.
- The LLM cache key now includes the real model id, so 4B and 14B completions never mix. The served name stays `drugkg-llm`, so models can be swapped without config changes.

### 2.2 Four experiments

| Experiment | Input | Processing | Chunks |
|---|---|---|---|
| `text_edc` | `data/text/*.txt` (section-structured raw text) | EDC | 854 |
| `decomp_edc` | decomposed sentences (same drug/section sentences packed up to 1,100 chars) | EDC | 911 |
| `decomp_edc_ec` | reuses `decomp_edc` extraction | + KGGen entity/relation canonicalization, as published | 911 |
| `decomp_edc_ec_g` | same | + same-type-only comparison and an instruction that different drugs/brands/doses are not duplicates | 911 |

- All experiments add the same structured-metadata triples (generic/brand/class/dosage form/related drugs, about 970).
- Entity canonicalization is a port of the Resolution stage of **KGGen** (Mo et al., 2025, arXiv:2502.09956, Stanford), following the public code: ① semhash (NFKC normalization, singularization, merge at similarity ≥ 0.95) → ② k-means into clusters of 128 → ③ per cluster, pop one item, show the LM its top-16 neighbours from BM25+embedding rank fusion, and take back "duplicates + representative alias" → ④ rewrite triples. The only deviation shared by both runs is a safety rule that never merges strings whose numbers differ ("1 mg" vs "5 mg"); the guarded variant (`_ec_g`) additionally restricts candidates to the same entity type and tightens the instruction.
- One bug in the port (the LM listing the same string twice broke removal) was fixed during the run and both canonicalization experiments were re-run.

### 2.3 Visualization tooling
`scripts/visualize_kg.py` produces, per KG, an interactive explorer (`kg_explorer.html`) and presentation PNGs (relation distribution, entity types, triples per drug, shared side effects, a radial 1-hop graph per drug, experiment comparison). The explorer supports entity search, 1-2 hops, relation/type filters, a 50-drug overview, a shared-side-effect view, an evidence sentence per edge, and CSV export.

## 3. Results

### 3.1 Time and cost

| Stage | text_edc | decomp_edc | decomp_edc_ec | decomp_edc_ec_g |
|---|---|---|---|---|
| Extraction (Extract+Define+Canonicalize) | 25.1 min, 4,732 calls, 3.89M input / 0.35M output tokens | 26.4 min, 5,127 calls, 4.15M / 0.38M tokens | (reused) | (reused) |
| Relation consolidation | 50 s | 70 s | – | – |
| KGGen canonicalization | – | – | 8.8 min, 5,471 calls | 14.2 min, 6,019 calls |

The 14B AWQ model ran about as fast as the 4B model (about 30 s per drug), because the whole GPU was available and throughput rose.

### 3.2 Model effect: 4B → 14B (same 50 drugs, raw text input)

| Metric | 4B (10-06) | 14B `text_edc` |
|---|---|---|
| Open triplets | 11,140 | 12,113 |
| Relation names matching the seed schema directly (direct) | 62.2% | 77.8% |
| Mapped by LLM verification (mapped) | 4,022 | 2,468 |
| Added to the schema (enriched) | 153 | 166 |
| Distinct raw relation names | 1,409 | 860 |
| Final triples / entities / relations | 11,267 / 6,544 / 147 | 12,233 / 7,529 / 149 |
| Audit: duplicate-surface groups / sentence-like concepts | 169 / 727 | 237 / 685 |

The 14B model uses seed relation names from the start far more often (62% → 78%), which cut verification calls by 40% and the number of distinct relation names from 1,409 to 860; triples rose by 9%. Entity-level problems (surface duplicates, sentence-like nodes) did not shrink with the larger model; they belong to the canonicalization stage, not the extractor.

### 3.3 Preprocessing effect: raw text vs decomposed sentences (both 14B)

| Metric | `text_edc` | `decomp_edc` |
|---|---|---|
| Open triplets | 12,113 | 13,180 |
| direct / mapped / enriched | 9,426 / 2,468 / 166 | 10,241 / 2,657 / 239 |
| Final triples / entities | 12,233 / 7,529 | 13,198 / 8,466 |
| Relations (40 seed + enriched) | 149 (+109) | 210 (+170) |
| Share of the top-10 relations | 66% | 61% |
| Audit: sentence-like / composite / relation-type mismatch | 685 / 606 / 267 | 781 / 636 / 361 |

Decomposition raised recall (+8% triples, +12% entities) but enriched relations grew from 109 to 170 and sentence-like entities and type mismatches also increased. Short decomposed sentences often lose their subject or context, so the LLM invents new relation names more often. Decomposition extracts "more", not "cleaner".

### 3.4 Entity canonicalization (KGGen) results

| Metric | Before (`decomp_edc`) | KGGen as published | KGGen guarded |
|---|---|---|---|
| Entities | 8,466 | 5,064 (−40%) | 5,669 (−33%) |
| Triples / relations | 13,198 / 210 | 11,940 / 143 | 11,746 / 130 |
| Merged entity pairs | – | 3,480 | 2,847 |
| Clusters mixing entity types | – | 641 | 11 |
| Relation clusters mixing negated/inverse relations | – | 5 | 3 |
| Audit: duplicate-surface groups | 235 | 53 | 68 |
| Audit: sentence-like / composite | 781 / 636 | 463 / 294 | 523 / 366 |
| Audit: entities violating a relation's type | 361 | 1,136 | 1,001 |

Surface duplicates dropped sharply, but **fact-changing over-merges** were frequent.
- As published: nine page drugs were merged into other drugs or broader concepts (Atorvastatin → Lovastatin, Escitalopram → citalopram, Carvedilol → "Non-cardioselective beta blockers", Gabapentin → gabapentin enacarbil). A `swelling` cluster of 27 items mixed facial swelling, leg swelling and lump in neck. Relation merging collapsed direction and negation: `causes` absorbed `caused by`, `administered via` absorbed `not administered via`, `treats` absorbed `are being treated with`.
- Guarded: type mixing nearly vanished (641 → 11), but Carvedilol → Metoprolol, Cetirizine → Levocetirizine, Duloxetine → Cymbalta (a brand) remained, and `low white blood cell count` absorbed hypoglycemia and low calcium. Relations stayed unstable, e.g. `has side effect` represented by `has symptom`.
- The rise of relation-type violations from 361 to over 1,000 reflects wrong merges blurring relation semantics.

**Interpretation.** KGGen's duplicate test targets tense, plural and abbreviation variants in general-domain text. In a drug domain where a one-letter difference (citalopram/escitalopram) or a body-site difference means a different fact, the 14B model read "same meaning" as "same topic". Relations are already canonicalized by EDC on their definitions, so adding KGGen's name-based relation merging destroys direction and negation. The safe, effective part was semhash plus surface-variant merging (singular/plural, case, modifiers).

### 3.5 Visualization outputs
- `output/viz/{main_4b, text_edc, decomp_edc, decomp_edc_ec_canon, decomp_edc_ec_g_canon}/kg_explorer.html` and `fig_*.png`, plus `output/viz/fig_experiments.png`.
- Three explorer views (drug overview, entity neighbourhood, shared side effects) were rendered in headless Chromium without errors. In the canonicalized KGs, KGGen renamed drug nodes such as Sertraline, so their ego figures are not generated; this is another instance of over-merging.

## 4. What is still needed

**Choosing the KG for the presentation**
- For now, use a pre-canonicalization KG. `text_edc` has the cleaner relation set and `decomp_edc` the higher recall; both are 14B results.

**Fixing canonicalization (next iteration)**
1. Exclude relations (`--no-canon-edges`) and canonicalize entities only.
2. Protect list: the 50 page-drug nodes and the parsed generic/brand names are excluded from merging, or merged only when metadata confirms the same active ingredient.
3. Second verification: for every pair KGGen proposes, ask "same real-world entity? no if different drug, dose, site or severity" and require an embedding-similarity floor (e.g. 0.85). Tightening the instruction alone was not enough.
4. Keep specificity: link more specific labels such as `severe swelling` with a `broader` edge instead of merging them.
5. Link drugs and conditions to external identifiers (RxNorm, MeSH) to reduce reliance on LLM judgment.

**Quantitative evaluation (needs human effort)**
- `output/experiments/<experiment>/entity_canon/merge_pairs_sample.csv` holds 120 merged pairs per variant; manual labelling gives a direct precision comparison of the two variants.
- Triple precision is still only sample-reviewed. Scoring a stratified sample of 100-200 triples per relation group would let the model swap and the preprocessing effect be reported as precision.

**Operations**
- The vLLM server is still running (about 21 GB of GPU memory). Stop it with `pkill -f "vllm serve"` before starting other GPU jobs.
- All LLM responses are cached per model, so re-running the same configuration finishes almost immediately. Reproduction commands are in section 5 of `261007-experiments.md` and sections 9-10 of the README.

## 5. Additional checks (10-08): relation over-merging and relation redundancy

### 5.1 How over-merging was checked

**Entities** (`output/experiments/<exp>/entity_canon/entity_clusters.json`, `scripts/audit_entities.py`)
1. Whether any of the 50 page-drug labels was remapped to another label (`entity_map.json`): 9 in the as-published run, 7 in the guarded run, all to other drugs or broader concepts.
2. Whether a cluster mixes entity types (types from the pre-canonicalization KG): 641 vs 11 clusters.
3. Whether strings with different numbers were merged (blocked by the safety rule: 0).
4. Manual review of the six largest clusters (`swelling` with 27 members, `vision changes` with 20, ...).
5. Audit metrics before/after (entities violating a relation's type: 361 → 1,136 / 1,001).
6. A sample of 120 merged pairs per run for manual labelling (`merge_pairs_sample.csv`).

**Relations** (`edge_clusters.json`; results in `output/report/relation_merge_audit.md`)
1. Whether relations with and without a negation (not / no / does not ...) share a cluster.
2. Whether inverse-direction relations (passive forms ending in "by", e.g. `causes` / `caused by`) share a cluster.
3. Whether the merged relations have different subject/object type signatures (schema domain/range).
4. Whether two or more hand-designed seed relations collapsed into one.
5. How many triples had their relation relabelled.

### 5.2 Relation over-merging results

| Metric | KGGen as published | KGGen guarded |
|---|---|---|
| Relation clusters | 25 | 24 |
| Relations merged | 92 | 104 |
| Triples relabelled | 4,194 (32%) | 5,073 (38%) |
| Clusters mixing negation | 4 | 3 |
| Clusters collapsing ≥2 seed relations | 4 | 7 |
| Clusters with several type signatures | 20 | 19 |

Relation over-merging was worse than entity over-merging. Representative cases:
- As published: `has side effect` absorbed has serious side effect, has overdose symptom, has withdrawal symptom and has symptom (three seed relations gone, 2,839 triples). `used in combination with` absorbed interacts with, use with caution in and used in population (1,485 triples). `reduces risk of` absorbed has increased risk in, has no identified risk of, increases level of and lowers level of (opposites and negations mixed). `causes` absorbed `caused by`; `administered via` absorbed `not administered via`.
- Guarded: the type guard applied to entities only, so relation merging grew. `has function` absorbed 15 relations including has brand name, has generic name, has dosage form and has availability (662 triples). `has dose` absorbed 8 relations including has recommended dose, has maximum dose and has missed dose instruction. `interacts with` absorbed should be avoided with, should not be taken with, compared with and differs from. `has symptom` became the representative of the whole `has side effect` family.

Conclusion: KGGen's relation merging is name-similarity based; it erases negation, direction and the dose-versus-instruction distinction, and undoes the definition-based relation schema EDC produced. The relation side of these runs must not be used, and the next iteration should exclude relations from canonicalization (`--no-canon-edges`).

### 5.3 Relation redundancy per KG (cosine similarity of relation definitions)

Method: the relation definitions in each KG's `schema.csv` were embedded with the same embedder used for EDC canonicalization (bge-base-en-v1.5) and all pairwise cosine similarities computed (`scripts/relation_redundancy.py`; details in `output/report/relation_redundancy.md`). Because every definition shares the template "The subject drug … the object entity", absolute values are high, so the hand-designed, intentionally non-redundant seed schema (40 relations: mean nearest-neighbour similarity 0.887, 81 pairs ≥ 0.85) serves as the baseline.

| KG | relations | mean nearest-neighbour sim | pairs ≥0.85 | pairs ≥0.90 | relations with a neighbour ≥0.85 | share of triples under those relations |
|---|---|---|---|---|---|---|
| seed schema only (baseline) | 40 | 0.887 | 81 | – | – | – |
| main (4B) | 147 | 0.840 | 187 | 13 | 66 | 93% |
| text_edc (14B) | 149 | 0.878 | 562 | 44 | 115 | 97% |
| decomp_edc (14B) | 210 | 0.881 | 934 | 77 | 162 | 98% |
| decomp_edc_ec canon | 143 | 0.869 | 425 | 34 | 98 | 97% |
| decomp_edc_ec_g canon | 130 | 0.866 | 361 | 17 | 91 | 90% |

How to read it:
- **Pairs ≥ 0.90** is the practical redundancy signal. The 4B KG has 13 such pairs, the 14B raw-text KG 44 and the decomposed-sentence KG 77. The 14B model matches seed names more often (78% direct), but the relations it still adds are often close in meaning to a seed relation; the decomposed input, with 170 enriched relations, is the most redundant.
- The most similar pairs are mostly seed/enriched combinations: `has dosage form` / `has formulation` 0.946, `treats` / `has use indication` 0.931, `has side effect` / `has side effect frequency` 0.938, `no dose change needed in` / `no dose adjustment needed with` 0.963. Many relations for which the verifier answered "None of the above" should have been mapped to a seed relation. The consolidate stage merging nothing is the weak point; these top-similarity pairs can be merged by a human from the ranked list without another LLM pass.
- Even within the seed schema, 81 pairs score ≥ 0.85 (`has brand name` / `manufactured by` 0.941, `treats` / `reduces risk of` 0.914, `has side effect` / `has serious side effect` 0.925). Embedding similarity alone would merge deliberately distinct relations, which is exactly why KGGen's relation merging failed: similarity should only propose candidates, and the decision must also look at definitions and type signatures.
- The canonicalized KGs show fewer relations and fewer pairs ≥ 0.90, but as section 5.2 shows this was obtained by merging relations with different meanings, so it is not a good signal.
